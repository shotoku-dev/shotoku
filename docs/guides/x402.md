# x402 Integration

x402 is an open payment protocol from Coinbase that lets a client pay for a resource over plain HTTP — no account, no API key, no login. It revives the long-dormant HTTP `402 Payment Required` status code and turns it into a pay-per-request handshake, settled in stablecoins (typically USDC).

That makes it a natural fit for agents: a machine can pay for exactly what it uses, per request, with nothing but a wallet that can sign.

Shotoku's job here is not to move the money. It is to decide, **before** the money moves, whether the agent is allowed to spend it.

> x402 is Shotoku's first payment rail. The same authorization model works for any rail.

---

## The 402 handshake

A single paid request takes two round-trips:

```txt
1. Agent requests a resource        GET /premium-data
2. Server answers  402 Payment Required
                                    + requirements: pay 0.05 USDC to 0xABC… on Base
3. Agent signs a payment with its wallet
                                    GET /premium-data  + X-PAYMENT header
4. Server verifies + settles on-chain, returns the resource
```

- **Step 2** carries the _payment requirements_: how much, which token, which network, and the recipient address.
- **Step 3** carries the _payment payload_: a signed authorization to transfer the stablecoin (for USDC, an EIP-3009 `transferWithAuthorization`). A facilitator verifies it and settles the transfer on-chain.

No password is ever exchanged. The agent proves it can pay by signing, not by logging in.

---

## Where Shotoku fits

Shotoku inserts itself **between step 2 and step 3** — after the agent learns the price, before it signs anything.

```txt
2. Server → 402: "pay 0.05 USDC to 0xABC…"
        │
        ▼
   ★  Shotoku.authorize()   ← the decision point
        │
   approved          → continue to step 3 (sign + pay)
   denied / pending  → stop, surface to a human
        │
        ▼
3. Agent signs and pays
```

This is the only moment where both of these are true at once:

- The agent **knows the full cost** — amount, recipient, and resource were just delivered in the 402.
- Nothing **irreversible** has happened yet — no signature, no settlement.

Before step 2 there is no amount to evaluate. After step 3 the money is already gone. That narrow gap is the only place an authorization layer can do its job.

## Mapping the 402 to an authorization request

**Everything in a 402 body is written by the server asking to be paid.** So the mapping is careful about where each field comes from:

| `AuthorizeRequest` field | Comes from                                                         |
| ------------------------ | ------------------------------------------------------------------ |
| `actor`                  | The agent making the request                                       |
| `action: "purchase"`     | It is a payment                                                    |
| `resource`               | The **host of the URL the agent requested** — never the 402's `resource` |
| `amount`                 | The 402 amount, converted with the asset's **registered** decimals  |
| `recipient`              | The 402 `payTo` — matched by `recipients` rules                    |
| `rail: "x402"`           | The protocol                                                       |

Why it matters:

- **Resource.** If the policy matched the 402's own `resource` claim, any server could say "I am `api.openai.com`" and collect payment to its own address. Shotoku uses the host the agent actually sent its request to, and refuses an option that claims a resource on a different host. Using the host, not the full URL, also keeps one vendor as one resource for `maxDailyAmount` — a query string cannot reset the budget.
- **Asset and amount.** x402 amounts are in atomic units, and what a unit is worth depends on the token. Shotoku identifies the asset by **network + contract address** against a registry (`KNOWN_X402_ASSETS`: USDC on Base and Base Sepolia) and takes decimals from there, never from the server's `extra.name` or an assumed 6. An option in an unregistered asset is refused. Without this, 5,000,000 atomic units of an 8-decimal token — 0.05 of it — would read as $5.
- **Recipient.** `payTo` becomes the request's `recipient`. Pin it with `recipients` on the rule, and a human approval of one payment cannot be redeemed for the same payment to another address. The asset and network are bound into the approval too.

```ts
import { authorizeX402Payment, parseX402Response } from "@shotoku/core";

// On receiving a 402 from `url`, before signing anything:
const requirements = parseX402Response(await res.json(), { requestUrl: url });
const decision = await authorizeX402Payment("agent-001", requirements, {
  policyPath,
  ledgerPath,
});

if (decision.approved) {
  // step 3: sign requirements.option — the exact option that was authorized —
  // and send the X-PAYMENT request
} else {
  // stop — the decision is recorded and waiting for a human
}
```

`parseX402Response` throws a `ShotokuError` (`request_invalid`) when it cannot trust the response: no option in a known asset, a resource on another host, a missing `payTo`, or a malformed amount. To accept another token, register it — and only register assets whose unit means what your policy limits mean (dollar stablecoins, if your limits are in dollars):

```ts
const extra = [{ network: "base", address: "0x…", symbol: "EURC", decimals: 6 }];
parseX402Response(body, { requestUrl: url, assets: extra });
authorizeX402Payment(actor, requirements, { policyPath, ledgerPath, assets: extra });
```

A policy for this rail can pin the vendor's address and cap the total on top of per-vendor limits:

```yaml
rules:
  - resource: api.weather.xyz
    recipients: ["0x000000000000000000000000000000000000dEaD"]
    verdict: approved
    maxAmount: 0.10
    maxDailyAmount: 1.00

budgets:
  - actor: "*"
    maxDailyAmount: 5.00
```

## What Shotoku does not do

Shotoku is an authorization layer, not a wallet.

- It never holds funds.
- It never stores private keys.
- It never signs or settles a payment.

The agent's own wallet signs. The facilitator settles on-chain. Shotoku answers one question — _should this payment be allowed?_ — and records the answer to the local ledger.
